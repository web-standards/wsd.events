Особенности обработки веб-страниц

Как браузер обрабатывает загружаемую страницу?

  • Отображение веб-страниц осуществляется в потоковом режиме
  • Стилевые правила применяются к каждому элементу сразу же после его создания внутри DOM
  • Вот наглядная демонстрация загрузки страницы в искусственно замедленном режиме

Основания для пересчета и возможной перерисовки

  • Первичное отображение документа
  • Изменение размеров
  • Изменения внутри DOM
  • Изменение стилей
  • Срабатывание по таймеру

Как анализируются CSS-селекторы?

.content ul li {…}

Обычно справа налево!

القاعدة

Является ли текущий элемент пунктом списка?

.content ul li {…}

Если да, следуем вверх по DOM, ищем элемент <ul>

.content ul li {…}

Нашли? Отлично! Следуем еще выше в поисках элемента с классом content

.content ul li {…}

Быстрые и медленные

Эффективность простых селекторов

Самые быстрые — такие селекторы, которые требуют меньшего количества проверок:

#intro {…}
.content {…}

Более медленные простые селекторы

В порядке снижения производительности, обусловленного возрастанием количества или усложнением проверок:

div {…}
* {…}
[title] {…}
:hover {…}

Комбинированные селекторы

В порядке снижения производительности, обусловленного возрастанием количества проверок:

h1 + p {…}
ul > li {…}
pre code {…}

Внешность обманчива

#intro * {…}

Избыточность не нужна!

header#intro {…}

#intro {…}

Это почти полностью справедливо и для селекторов по классу

Еще один примерчик устранения избыточности

body ul.navigation li a {…}

.navigation a {…}

Общие рекомендации

  • Не используйте * справа
  • Делайте селекторы максимально специфичными
  • Устраняйте избыточные уточнения
  • Вместо комбинированных селекторов используйте селекторы по классу

См. Google Page Speed

Впрочем, чувство меры не помешает

Google Page Speed рекомендует:

ul li {color: blue;}
ol li {color: red;}

.unordered-list-item {color: blue;}
.ordered-list-item {color: red;}

Занятные истории

И последние станут первыми?

Странное, казалось бы, дело:

  • E:first-child — определен в CSS2
  • E:last-child — описан только в CSS3 и реализован в браузерах намного позже

Второй при честной реализации требует больше ресурсов

E:last-child не везде реализован по-честному

Можно сравнить отрисовку меню навигации в замедленном режиме в различных браузерах

  • Честные реализации: Firefox, IE
  • Не вполне честные: Chrome, Safari, Opera

Все лучшее — детям?

Давно и успешно реализованы:

  • div p — селектор потомка
  • div > p — селектор дочернего элемента, то есть прямого потомка

Рассчитывать ли нам на селектор предка или селектор родителя?

  • div:has(p) — существует в jQuery

Как это могло бы реализоваться в CSS? Код разметки

<section class="content">
	<h1>Заголовок</h1>
	<p>Текст первого абзаца.</p>
	…
	<p>Текст еще какого-то абзаца с <code>фрагментом кода</code>.</p>
	…
</section>

Как это могло бы реализоваться в CSS? Код таблицы стилей

.content:has(code) {
	line-height: 1.5;
 }

Условия установления применимости правила

  • Обнаружен первый вложенный элемент <code>
  • Полностью загружены все элементы, находящиеся внутри <section>

Дополнительные проблемы

  • Как только встретится <code>, потребуется перерисовать <section>
  • Применение правила затрагивает наследуемые свойства ⇒ производится перерасчет и перерисовка каждого потомка элемента <section>

Целевые объекты селектора

По умолчанию subjects определяются крайней справа частью селектора:

.content pre code {…}

Принудительное переопределение целевых объектов в CSS4

ol > li:only-child {…}

ol! > li:only-child {…}

Одна и та же структура DOM-дерева, но различные целевые объекты

С цифрами на руках

Как выяснить порядок различий?

  • Сгенерируем несколько документов
  • Структура документов — «как в жизни»
  • Разметка — одна, внешний вид — один, наборы селекторов — разные
  • Объем каждого файла — чуть более 300 килобайт
  • Каждый документ содержит 3000 элементов <p>
  • Каждая таблица стилей включает 300 CSS-правил

Устройство тестовых файлов

	<section id="s1" class="s1">

Методика измерения

Перед таблицей стилей, внутри <head>…</head>:

var $startTime = (new Date()).getTime();

Перед закрывающим тегом </body>:

window.onload = function() {
	var $processDuration = (new Date()).getTime() - $startTime;
}

Более тонкий инструмент — профайлеры

  • Позволяют детально протоколировать все события, связанные с обработкой кода разметки и таблиц стилей, с применением селекторов, с перерасчетом и перерисовкой элементов страницы
  • Существуют для Opera (недавно интегрирован в экспериментальную сборку Dragonfly) и для Webkit
  • Интересно сопоставить результаты наших тестов с тем, что фиксируется профайлерами

Краткие выводы

С одной стороны…

  • «Хорошие» селекторы: почти незаметный вклад в «торможение» даже при изрядном количестве правил
  • «Плохие» селекторы: способны замедлить обработку таблицы стилей в разы
  • Одно правило с «плохим» селектором порой сто́ит сотни правил с «хорошими»

С другой стороны…

  • Максимально достижимая экономия в реальной практике — десятки миллисекунд
  • Бескомпромиссная погоня за производительностью может повредить здравому смыслу
  • Не надо совсем отказываться от ресурсоемких селекторов — нужно просто использовать их благоразумно

Пара частностей

Идентификаторы или классы?

  • Одинаковая производительность
  • У селектора по классу меньшая специфичность
  • id уникален

Что именно использовать? Решайте сами в зависимости от задачи!

Вполне нормальная практика

	}

	}
